# 시나리오 3 (보조): 메일 게이트웨이 root 탈취 + 로그 삭제 — 플레이북 범위 밖

> 모든 데이터는 가상입니다. 회사·인물·IP는 실제와 무관합니다.
> IP는 문서용 예약 대역(RFC 5737: 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24)만 사용합니다.

## 가상 조직
- 회사: (주)한빛물류 (가상) — 임직원 약 300명, 자사 홈페이지·고객 문의 메일 운영 → 정보통신서비스 제공자
- 대상 서버: `mx-gw01.hanbit.example` (메일 게이트웨이, 내부 IP 10.20.1.15)
- 내부망 DNS 서버(Windows): 10.20.1.9 — 이미 감염된 상태에서 공격 출발지로 쓰임
- 메일 보관 고객 문의: 약 4,200명분 (이름·연락처·주소 포함, 주민번호 없음)

## 기대 결과
- 유형: 관리자 권한 탈취 (P1)
- 경고: 재부팅·재설치 금지, 프로세스 즉시 삭제 금지
- 신고: 침해사고 신고 대상 → 마감 11/20(금) 08:50
- 개인정보: 유출 "의심" + 외부 불법접근 → 유출 신고 검토 대상, 통지 검토 → 마감 11/22(일) 08:50
- 문서: 침해 최초신고서, 유출 신고서(의심), 정보주체 통지문, 경영진 보고서, 타임라인

## 데모 입력 순서
1. "방화벽에서 메일 서버가 외부 3389로 통신한다는 알림이 왔어요" (인지 시각 기록)
2. `remote_syslog_secure.log` + `firewall_alert.csv` 붙여넣기
3. "고객 문의 메일이 4,200명분 정도 있어요. 주민번호는 없어요."

## 상태 (v0.3): 보조 시나리오 — "범위 밖" 처리 시연용
플레이북은 서버 자체 장악(root 탈취·악성코드)을 범위 밖으로 둡니다(2쪽 "이 문서가 다루지 않는 것").
이 시나리오에서 에이전트의 정답 행동은 **아는 척하지 않고** 초동 조치(차단·보존·보고) + 신고 기한 계산까지만 하고
"전문 대응 조직 즉시 호출"을 권고하는 것입니다. 심사 Q&A의 "AI가 모르는 상황이면요?"에 대한 답으로 씁니다.

- 탐지 규칙: `data/log_rules_selfhosted.json` (v0.3에서 추가)
- 엔진: `secuaid/detect.py` 의 `SR_*` / `FW_OUTBOUND_RDP` 규칙
- 주의: 서버 로컬 시간(KST)으로 적힌 secure 로그를 UTC로 오인하지 않도록 `assume_utc=False`로 파싱합니다.
