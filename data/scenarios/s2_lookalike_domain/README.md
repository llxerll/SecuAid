# 시나리오 2 (대조군): 유사 도메인 사칭 — 우리 계정은 침해되지 않았다

> 모든 데이터는 가상입니다. 회사·인물·도메인·계좌는 실재하지 않습니다.
> IP는 문서용 예약 대역(RFC 5737)만, 도메인은 `.example`만 씁니다.

## 왜 이 시나리오가 필요한가
S1(계정 침해)만 보여 주면 "에이전트가 무조건 '침해됐다'고 하는 것 아닌가"라는 질문을 피할 수 없습니다.
S2는 **판별을 하지 않는 에이전트와 하는 에이전트의 차이**를 보여 주는 대조군입니다.
정답은 "우리 계정은 안전하다. 대신 사칭 도메인 차단·고객 경고·DMARC 점검을 하라"입니다.

## 상황
- (주)한빛물류 `hanbit-logis.example` (직원 38명)
- 공격자 도메인: `hanbit-logistcs.example` (회사명을 그대로 포함한 변형, SPF fail / DMARC fail)
- 고객사 회계 담당이 계좌 변경 메일을 전달하며 확인 요청 → 11/19(목) 14:20 인지
- 사내 로그인·감사 로그에는 이상 없음(서울 사내 IP만, 숨김 규칙·외부 발송 없음)
- 함정: 사칭 메일 본문에 실제 인보이스 번호(HB-2611-0447)와 금액(18,700,000원)이 들어 있음
  → "내부 정보가 담겼다"면 내부 침해를 배제할 수 없다. 에이전트는 이 점을 확인 항목으로 남겨야 한다.

## 기대 결과 (에이전트 평가용)
- 판별: **유사 도메인 사칭(lookalike)** — 확인 수준. ATO 아님.
- 심각도: **P4** (내부 접근 흔적 없음)
- 신고: 침해사고 신고 **비해당/검토**(우리 시스템 침해 없음), 개인정보 유출 신고·통지 **비해당**
- 할 일: 수신 차단 규칙, 고객·거래처 공식 채널 경고(T1), 직원 공지(T3), 내부 침해 여부 기본 점검, DMARC 정책 점검
- 하지 말 것: "외부 사칭"으로만 단정하고 내부 정보 유출 가능성 점검을 생략하는 것
- 문서: T1(고객 경고), T3(직원 공지), T6(경영진 5줄), 경영진 보고, 타임라인

## 데모 입력
1. "고객사에서 저희 도메인과 비슷한 주소로 계좌 변경 메일을 받았다고 전달해 왔습니다. 방금 확인했어요."
2. `lookalike_account_change.eml` 붙여넣기
3. `entra_signin_log.csv` + `audit_log.csv` 붙여넣기
4. "저희 계정에서 나간 흔적은 없는 것 같습니다. 이거 우리가 신고해야 하나요?"
