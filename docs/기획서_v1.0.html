#반복되는 실수왜 치명적인가
1원인부터 찾느라 돈을 늦게 막음사칭 메일에 송금이 나갔다면 은행 지급정지 요청이 분 단위 싸움입니다. "일단 원인을 알아보고"가 회수 가능성을 깎습니다
2암호만 바꾸고 해결됐다고 보고공격자는 세션 토큰, 앱 비밀번호, 숨김 규칙으로 다시 들어옵니다. 실제 대응에서 가장 흔한 재침입 경로입니다
3당황해서 증거를 지움의심 규칙을 없애거나 PC를 포맷하면, 유출 범위를 증명할 근거가 사라지고 신고·보험 청구가 어려워집니다
4신고 대상자, 기한을 인제인지 모름침해사고는 인지 후 24시간, 개인정보 유출 신고와 정보주체 통지는 72시간 안에 해야 합니다. 기한은 "관계자 누구든 처음 안 시점"부터 흐릅니다
5침해된 계정으로 사과 메일 발송"방금 메일 무시하세요"를 같은 계정으로 보내면 공격자에게 들키고, 받는 쪽은 그도 피싱인지 구분할 수 없습니다

왜 지금, 왜 이 사람들인가

  • 대기업은 이 문제가 없습니다. 보안관제·사고대응팀과 계약된 외부 전문가가 있습니다. 문제는 그 사이에 있는 수많은 작은 회사입니다.
  • 기존 자료는 "읽는 문서"입니다. 가이드와 체크리스트는 있지만, 사고 당일 당황한 사람은 수십 쪽을 읽고 자기 상황에 맞는 줄을 찾지 못합니다.
  • 법이 계속 바뀝니다. 개인정보 유출 "가능성"만으로도 통지가 필요해지는 등 규정이 강화되는 추세라, 작년 지식으로는 판단이 틀릴 수 있습니다. 그래서 규칙 테이블에도 검증일(2026-11-04)과 함께 "시행령 제39조 2026.9 개정 반영 — 재확인 필요" 같은 표시를 남기고, 실행할 때마다 Liner Search Agent로 조항을 다시 읽어 코드 규칙과 어긋나면 화면에 드러냅니다.
"신입이 반복하는 실수"를 "누구나 피하는 실수"로.

이 해커톤이 말하는 "오래 일하며 발견한 병목을 내 노하우로 푸는 에이전트"에 정확히 해당하는 문제라고 생각합니다. 이 노하우는 이미 55쪽 플레이북으로 정리되어 있고, 에이전트는 그것을 사고 당일에 실제로 쓰이게 만드는 수단입니다. 판단 기준은 사람의 경험에서 나오지만, 그 판단을 같은 입력이면 같은 결과가 나오는 코드로 옮겼다는 점이 이 프로젝트의 성격입니다.

2. 해결 방법: 노하우를 에이전트로 옮기기

에이전트는 사람을 대신해 판단하지 않습니다. 사고 당일 사람이 같은 순서로, 같은 근거를 보며 판단하도록 만듭니다. 대화는 다섯 단계로만 진행하고, 각 단계의 출력은 사건 보드에 남습니다.

① 인지

"거래처에서 우리가 계좌를 바꿨냐고 전화가 왔어요"
→ 인지 시각 기록, 마감 시계 시작, 추가 질문
② 판별

메일 원본(헤더 포함) 붙여넣기
→ 계정 침해 / 스푸핑 / 유사 도메인 구분과 근거
③ 통제

로그인·감사 로그 붙여넣기
→ 지금 할 일 12개, 하지 말 것, 지속성 점검, 증거 보존
④ 판단

"이미 1,870만 원을 송금했대요"
→ P1 격상, 은행 우선 행동, 신고·통지 대상과 마감
⑤ 문서

"신고해야 하나요?"
→ 근거 있는 판단 + 초안 10종 + 발송 전 통과표

플레이북에서 에이전트로 옮긴 것

3.2 심각도 P1~P4, 에스컬레이션 표등급 판정과 "누구를 불러야 하나" 안내새 사실이 나올 때마다 재평가

모든 항목에 플레이북 쪽·절 번호를 붙여 두었습니다. 그래서 에이전트의 권고에는 항상 "근거: 플레이북 12.2"처럼 출처가 표시됩니다. 플레이북 원문(판매 중인 저작물)은 저장소에 포함하지 않고, 구조화한 판단 기준만 사용합니다.

에이전트가 지키는 원칙

확인 / 추정 / 미확인을 섞지 않는다

모든 보고·공지문에서 세 가지를 구분합니다. "조사 결과 없음"을 "피해 없음"으로 바꿔 쓰지 않습니다. 모든 사실은 Fact(value, level, source)로 저장되고, 화면·문서·응답이 수준을 항상 표시합니다.
모르는 건 모른다고 한다

서버 자체 장악·랜섬웨어처럼 플레이북 범위 밖이면, 초동 조치와 기한 계산까지만 하고 전문 대응 조직 호출을 권고합니다. 서버 로그 시나리오(S3)에서 이 태도를 그대로 보여 줍니다.
제출은 사람이 한다

신고서·통지문은 초안까지만 만듭니다. 최종 판단과 발송은 담당자와 전문가가 합니다. 법률 자문이 아님을 문서마다 표시합니다. 자동 제출 기능은 만들지 않았습니다.
민감정보를 밖으로 보내지 않는다

로그를 모델에 보내기 전에 계좌번호·전화번호·주민번호·이메일을 마스킹하고, 원본 증거는 사용자 쪽에만 남깁니다. 매핑은 메모리에만 두고 디스크·로그에 쓰지 않습니다.

규칙과 모델이 어긋날 때 (drift)

실행 중 Liner Search Agent가 규칙과 다른 기한·요건을 말하면, 에이전트는 규칙을 조용히 덮어쓰지 않고 drift로 표시해 둘을 나란히 보여 줍니다. 조항 개정 여부는 기계가 확정할 수 없고, 확인해야 할 대상이기 때문입니다. 같은 이유로 모델에게는 "JSON에 없는 수치·법령·기관명을 만들지 말 것"을 프롬프트로 제한하고, 응답이 JSON을 벗어나면 한 번 더 교정을 요청한 뒤 그래도 실패하면 규칙 결과만 남깁니다. AI가 조용히 틀리는 것보다, 틀릴 수 있는 지점을 화면에 드러내는 편이 사고 대응에 맞다고 판단했습니다.

v0.9에서 이름을 바로잡았습니다 — 실제로 호출하는 Liner API 3종

v0.9 기획서의 Liner Legal Search는 플랫폼에 없는 이름이었습니다. 2026-11-15 콘솔과 라이브 호출(HTTP 200)로 확인한 실제 구성은 Router · Tools · Agent 3계열이고, 이 프로젝트는 그중 아래 3개를 실제로 호출합니다. 심사에서 감점 요인이 될 수 있는 부분이라 v1.0에서 먼저 밝힙니다.

Liner API가 꼭 필요한 이유

  • Search가 없으면 위험한 에이전트가 됩니다. 침해 대응에서 오래된 정보는 곧 오판입니다. 개인정보보호법 시행령은 2026년 9월에 개정되었고, 규칙 테이블에도 검증일과 "재확인 필요" 표시가 붙어 있습니다. 실행할 때마다 조항을 다시 읽어 규칙과 어긋나면 경고합니다.
  • Search·Search Agent로 법령 근거를 붙입니다. 기한 카드마다 근거 조항과 출처 링크가 함께 나옵니다. "24시간"이 어디서 나왔는지 담당자가 확인할 수 있어야 신고를 맡길 수 있습니다.
  • liner-mark가 전체를 지휘합니다. 사람의 말을 구조화된 사실로 바꾸고, 어떤 도구를 언제 부를지 결정하는 두뇌입니다. 대화 이력을 함께 보내 문맥이 이어집니다.
시연에서 보여 줄 장면

신고 판단 단계에서 에이전트가 Search Agent로 정보통신망법 제48조의3과 개인정보보호법 제34조를 조회해 "24시간·72시간"과 그 요건을 출처 링크 16~52건과 함께 제시하고, 코드 규칙과 대조해 "차이 없음"을 표시하는 장면. Liner API가 장식이 아니라 판단의 정확도를 책임지는 부분임을 보여 줍니다. S1 전 구간 라이브 실행은 38.4초(Mark 7회 + Search Agent 1회 + Search 1회)였고, 키가 없으면 규칙 기반 모드로 자동 전환되어 데모가 멈추지 않습니다.

개발하며 잡은 실한 함정

① 기준 국가가 공격자 쪽으로 뒤집힌 사례. 처음 탐지는 "사용자가 가장 자주 로그인한 국가"를 정상 기준으로 삼았습니다. 그런데 시나리오에서 공격자의 로그인이 피해자보다 많아, 기준 국가가 공격자 쪽(네덜란드)으로 뒤집히고 정상 서울 로그인이 의심으로 표시되었습니다. 실제 사고에서도 공격자가 며칠간 머문 계정은 같은 상황이 됩니다. 기준을 "조직 기준 국가, 없으면 시간순 첫 로그인 국가"로 바꿔 해결했고, 이 사례를 회귀 테스트로 남겼습니다.

② v0.3에서 추가로 닫은 세 가지. 규칙 문서에는 "60분 내 두 국가"가 있는데 코드는 CorrelationId만 보고 있었습니다(조건 미구현). 감사 로그의 Send는 아예 탐지하지 않아, 기획서에 쓴 "발송"의 근거가 비어 있었습니다. 표기 없는 UTC 값을 서버 로컬 시간으로 읽어 기한이 9시간 어긋났습니다. 세 가지 모두 고치고 테스트로 고정했습니다. 그 결과 S1 탐지 건수는 v0.2 기준 23건에서 25건으로 늘었는데, 왜 늘었는지가 감사 기록으로 남는 쪽이 낫다고 판단했습니다.

이 과정에서 드러난 공통점은, 에이전트가 틀리는 지점이 대부분 "판단"이 아니라 계산과 입력 해석이었다는 것입니다. 그래서 v0.3은 모델 프롬프트를 늘리는 대신 규칙과 파서를 고치는 데 시간을 썼습니다.

① 실행 — 저장소를 clone하고 pip install -r requirements.txt(Flask 1개, 선택 python-docx) 후 python app.py → http://127.0.0.1:8000. ② 키 — .env.example을 .env로 복사해 LINER_API_KEY만 넣으면 Liner 3종이 켜집니다(모델은 LINER_MODEL로 교체 가능). ③ 없이도 동작 — 키가 없으면 규칙 기반 모드로 자동 전환되어 판정·기한·문서가 그대로 나옵니다. ④ 재현 — 오른쪽 위 시나리오 선택 후 [시나리오 실행], 또는 python run_demo.py --offline --out out/s1. 저장소에는 키·실데이터가 없고, 모든 로그와 메일은 가상입니다.

  • 신고 체계 확장: 공공기관 신고 체계, 금융권 정보유출 기준, 업종별 규칙을 추가할 수 있습니다. 규칙은 JSON이라 코드 수정 없이 늘릴 수 있습니다.
  • 콘솔 직접 연동(장기): 사용자가 승인하면 관리 콘솔 API로 로그를 직접 가져오고, 세션 철회 같은 조치를 "승인 후 실행" 방식으로 지원합니다. v0.3은 붙여넣기와 승인 게이트까지입니다.

8. 한계와 책임 있는 사용
  • 법률 자문이 아닙니다. 신고·통지 판단은 근거와 함께 "검토 대상"으로 제시하고, 최종 판단은 개인정보 담당자·법무가 합니다. 자동 제출은 기능으로 만들지 않았습니다.
  • 탐지는 1차 선별입니다. 로그가 없거나 보존 기간이 지나면 "미확인"으로 표시하고, 결과가 없다는 이유로 피해 없다고 말하지 않습니다.
  • 범위 밖은 넘깁니다. 서버 장악, 랜섬웨어, 포렌식이 필요한 사고는 초동 조치 후 전문 대응 조직 호출을 권고합니다.
  • 데이터: 시연과 저장소의 모든 데이터는 가상입니다. 실제 사용 시 원본 증거는 사용자 쪽에만 보관하고 모델에는 마스킹된 내용만 보냅니다. API 키는 환경변수로만 읽고, 저장소에는 값 없는 예시 파일만 두었습니다.
